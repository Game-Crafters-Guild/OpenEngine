How a game reads the keyboard, the mouse, gamepads, and pointer lock, and how the editor and the Player deliver that input to it. Every API item shows its C++ and its C# form: pick a language on any code view and the whole site follows. Input actions and bindings from C# are covered in [Play mode, input and ECS](../scripting/play-mode-input-ecs.mdx).

## How input reaches a game

- **Routing.** Each window passes its platform events through stages in order: the editor's own UI (in the editor), the game's UI (the HUD), the game, and last the window's own input. A press stops at the first stage that acts on it: a button that was clicked, a field that took a key, or a key the game reads. Releases reach every stage, so a key or button is never left down.
- **The play surface.** The part of a window the game runs in: in the editor, the Game View while play runs and its tab is active; in the Player, the whole window. Only input on the play surface reaches the game.
- **The game's input system.** The game reads one `Input::InputSystem`, which receives the raw events (keys, characters, mouse moves and buttons, the wheel, gamepads, and focus) and keeps the state a game polls. Reading a key or button claims it for the game, so in the editor it does not also fire an editor shortcut during play.
- **Per-frame state.** The input system takes a snapshot once a frame, before game systems run. "Pressed this frame", "released this frame", and the mouse delta describe the events delivered before that snapshot. They read the same however late in the frame the game reads them.

## Keys and mouse buttons

Three questions per key or button: is it down, was it pressed this frame, and was it released this frame. The "this frame" pair reports a press and release that complete inside one frame, which an is-down poll loses.

::::tab[C++]


## Mouse position

Where the last move placed the pointer: in the editor, in the Game View's pixels from its top-left corner; in the Player, in the window's. The position stands after the pointer leaves the window, so check `IsPointerInWindow` and `IsWindowFocused` before acting on it.

## Mouse delta

How far the mouse moved over the last frame: the movement delivered before this frame's input snapshot.

- **Unlocked**, the delta is in the units of the mouse position, counts only movement between two positions inside the window (a pointer entering from outside adds nothing). It stops when the cursor stops at the screen edge.
- **Locked** (see [Pointer lock](#pointer-lock)), the delta keeps counting however far the mouse travels. It is in the window's cursor units, the same in the editor and the Player and unaffected by the editor's UI scale: raw, unaccelerated device counts where the platform offers raw mouse motion (Windows, Linux X11), otherwise cursor pixels. A sensitivity tuned in the editor holds in the Player.
- When the lock begins or ends, the platform moves the cursor (to the window's center, then back to where the lock began). That move is not counted: the delta starts again from the first position after the change.

## Pointer lock

For mouse look, mouse steering, or anything else where the mouse moves the game rather than a cursor, the game asks for the pointer to be locked. The cursor is hidden and held by the window, and the mouse reports movement without bound. The game asks, the host (the editor or the Player) decides when to grant it, and the game reads the outcome each frame.

- **The request** stands until the game withdraws it or play ends. Ending the session clears it along with every action registration, so the next session starts unlocked.
- **The grant** is the host's. The game reads where the lock stands each frame as one of three states, below. Read movement as mouse look only while it is `Locked`.
- While the pointer is locked, its moves, clicks, and wheel reach only the game: no editor panel or HUD element hovers or clicks under a cursor that is not there. Releases still reach every stage. The mouse position runs on without bound and names no place on screen.
- A game that releases the lock itself, for a pause menu say, withdraws its request and asks again when it resumes.

| State | Meaning |
| --- | --- |
| `Unlocked` | The game does not ask for the lock. |
| `Pending` | The game asks and the host has not granted it yet: in the editor, play is paused, the Game View is not the active tab or its window has no focus, or <kbd>Esc</kbd> handed the pointer back; in the Player, the window has no focus; in the browser build, always. Show a prompt such as "click to play". |
| `Locked` | The host holds the pointer locked for the game this frame. |

:::::tabs
::::tab[C++]

| Call on `Input::InputSystem` | Contract |
| --- | --- |
| `LockPointer()` | Asks for the lock. The request stands until `UnlockPointer()` or the session ends. |
| `UnlockPointer()` | Withdraws the request. |
| `GetPointerLockState()` | Where the lock stands this frame: `Input::PointerLockState::Unlocked`, `Pending`, or `Locked`. |

The host reports its grant through the input system's raw input interface, not through these calls, so a game cannot claim a lock the platform does not hold. There is no change event: read the state each frame.

A mouse-look system, written as a project's native script, that says "click to capture" while the lock is pending:

```cpp title="MouseLookSystem.h"
#pragma once
#include <GameSDK/System.h>
#include "Core/Engine.h"
#include "Input/InputSystem.h"

struct MouseLookSystem : ECS::SystemBase
{
    float Yaw = 0.0f;
    float Pitch = 0.0f;
    // The HUD shows "click to capture" while this is set.
    bool ShowCapturePrompt = false;

    void OnStart(ECS::World&)
    {
        GameEngine::EngineCore::GetInstance().GetRuntimeInput()->LockPointer();
    }

    void OnUpdate(ECS::World&, float)
    {
        using GameEngine::Input::PointerLockState;
        auto* input = GameEngine::EngineCore::GetInstance().GetRuntimeInput();
        const PointerLockState lock = input->GetPointerLockState();
        ShowCapturePrompt = lock == PointerLockState::Pending;
        if (lock != PointerLockState::Locked)
            return;
        const auto delta = input->GetMouseDelta();
        Yaw += delta.x * 0.1f;
        Pitch -= delta.y * 0.1f;
    }
};
```

A mouse-look system that says "click to capture" while the lock is pending:

```csharp title="MouseLook.cs"
using GameEngine.Scripting;

public class MouseLook : GameSystem
{
    public float Yaw;
    public float Pitch;
    // The HUD shows "click to capture" while this is set.
    public bool ShowCapturePrompt;

    public override void OnEnable() => Input.LockPointer();

    public override void OnDisable() => Input.UnlockPointer();

    public override void OnUpdate(float deltaTime)
    {
        PointerLockState lockState = Input.GetPointerLockState();
        ShowCapturePrompt = lockState == PointerLockState.Pending;
        if (lockState != PointerLockState.Locked)
            return;
        var delta = Input.GetMouseDelta();
        Yaw += delta.X * 0.1f;
        Pitch -= delta.Y * 0.1f;
    }
}
```

## Gamepads

`IsGamepadConnected`, `GetGamepadAxis` and `IsGamepadButtonDown` read up to four pads in the Xbox layout (`GamepadCodes.h`). A pad that is connected when the game starts arrives a few frames later, as a pad plugged in during play does.

Each gamepad axis has the same range and sign on every platform:

| Axis | Range | Sign |
|---|---|---|
| `LeftX`, `RightX` | -1 to 1 | +1 with the stick pushed right |
| `LeftY`, `RightY` | -1 to 1 | +1 with the stick pushed up |
| `LeftTrigger`, `RightTrigger` | 0 to 1 | 1 with the trigger pulled fully |

To invert an axis, bind it with a negative scale. `BindGamepadAxis` takes the scale as its last argument: with a scale of -1, `RightY` gives +1 with the right stick pushed down.

On Windows, gamepads read through Microsoft GameInput. Windows 10 version 1903 and newer can run it, but Windows does not always install it. Put the GameInput redistributable in your game's installer (Microsoft's package `Microsoft.GameInput`, `GameInputRedist.msi`). The engine does not install it.

| Pad on Windows | How it reads |
|---|---|
| Xbox and Xbox-compatible pads | Through GameInput's gamepad layout. |
| Other pads, for example a DualSense or a Switch Pro controller | GameInput gives the pad's raw controls. The engine finds the pad's USB vendor and product id in the community mapping database SDL_GameControllerDB and maps the controls to the Xbox layout. A pad that the database does not list does not read as a gamepad, and the log names it once. |

On macOS, gamepads read through Apple's Game Controller framework, which is part of macOS. The engine reads every pad that the framework gives with its extended gamepad profile: Xbox, DualShock 4, DualSense, and MFi pads, and since macOS 13 many other Bluetooth and USB pads. The framework maps these pads to the Xbox layout, so the engine uses no mapping database on macOS. A pad that the framework does not support does not read as a gamepad. A pad without the extended gamepad profile does not read as a gamepad either, and the log names it once. The framework sends a pad's input only while the game is the frontmost application. On macOS, `GetGamepadRuntimeState()` changes from `Starting` to `Available` and stays there.

Read `GetGamepadRuntimeState()` before you ask the player for a gamepad:

| State | Meaning |
|---|---|
| `Starting` | The engine is still starting the gamepad runtime. No pad reads as connected yet. A headless application starts no gamepad runtime, so the state stays `Starting`. |
| `Available` | Gamepads work. |
| `RuntimeMissing` | The PC does not have GameInput, so gamepads are off. Show the player: "Install the GameInput runtime from Microsoft, then restart the game to use a gamepad." |
| `Failed` | GameInput is installed but did not start, so gamepads are off. The log has the error code. |

The game starts and runs in all four states. The log names the state once, at start.

## In the editor

- The game's input is live while play runs and the Game View is the active tab of its window.
- Entering play brings the Game View to the front of its tab group and gives it the keyboard focus, so the game's keys do not go to the panel you used last. A closed Game View stays closed.
- A key goes first to the editor control that has the keyboard focus. If you click a text field or a panel during play, that control takes the keys it uses.
- Stopping play brings back the tab that was in front of the Game View before play and gives the keyboard focus back to the control that had it. If you picked another tab or moved the focus during play, your choice stays.
- The pointer is locked while play runs unpaused, the game asks, and the Game View's window has focus.
- <kbd>Esc</kbd> hands the pointer back to the editor. The game still receives the key, and its request stands.
- Leaving the window while locked (switching to another application) also hands the pointer back, so coming back with a click on another panel uses that panel.
- A click on the Game View returns the pointer to the game.
- Pausing, stopping, or the game withdrawing its request ends a hand-back: resuming play locks again without a click.

## In the Player

The whole window is the play surface. The Player holds the lock for as long as the game asks and the window has focus. The platform lets the cursor go while the window is unfocused and takes it back when it regains focus. `GetPointerLockState()` reads `Locked` only while the lock is held.

## In the browser build

Pointer lock is not available: the request is kept but never granted, and `GetPointerLockState()` reads `Pending` while the game asks. A browser grants pointer lock only inside a click handler, which the per-frame grant is not.
