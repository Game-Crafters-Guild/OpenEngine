---
title: Package data model
description: Where every piece of package data lives (the package, the consuming project, and the machine cache) and which copy owns it.
---

Three storage worlds exist: **the package itself**, **the consuming project**, and **the global machine cache** (git packages only). The rule that makes everything work: *a package's asset identity and metadata live with the package; everything derived or project-specific lives outside it.* The code behind it is `PackageResolver`, `PackageMounts`, and `PackageGitSource`.

## The three worlds on disk

### An embedded or local (`file:`) package: mutable, watched

```text title="An embedded or local package on disk"
<project>/Packages/my-pack/            ← or any file: path; THE PACKAGE (author-owned, committed by its creator)
  package.json                          manifest: name, version, deps, modules, defines, assets root
  Assets/                               the package's asset tree — MOUNTED as its own source (alias = pkg name)
    Textures/water.png                  GUID = hash(alias + "textures/water.png") — derived, deterministic
  AssetDatabase.assetdb                 the package's OWN metadata store (types, KV) — writes land HERE, never in the project DB
  .Cache/AssetDatabase/                 the package's derived cache (SQLite: fingerprints, dep edges) — safe to delete
  .Cache/NativeScripts/                 native module builds for file:/embedded packages (build + active DLLs)
  Runtime/ Editor/ Native/              module source roots per package.json "modules"
```

### A git package: immutable, read-only, unwatched

```text title="A git package in the machine cache"
%LOCALAPPDATA%/GameEngine/PackageCache/
  my-pack@1.2.0-a1b2c3d4e5f6/           pristine checkout at the pinned commit (.git stripped), NEVER mutated
    package.json, Assets/, ...          payload only
  .native/my-pack@-<hash>/<build>/     native module builds, OUTSIDE the payload so the entry stays pristine

<project>/.Cache/AssetDatabase/Packages/my-pack/
                                        the package's derived asset cache for this project (a package that
                                        publishes an .assetmanifest; one without keeps its metadata in memory)
```

### The consuming project

```text title="The consuming project"
<project>/
  Packages/manifest.json                what you depend on: {"my-pack": "file:../shared/my-pack" | "embedded" | "git+https://...#v1.2.0"}
  Packages/packages-lock.json           pins: url, ref, exact commit, integrity — committed for reproducibility
  Packages/<name>/                      embedded packages live inline here
  AssetDatabase.assetdb                 PROJECT assets only — no package records leak in
  .Cache/                               project-derived data
  GameEngine.Scripts.csproj             generated; bakes <Reference> items to package assemblies
  ScriptAssemblies/                     compiled project scripts
    Packages/MyPack.dll                 compiled PACKAGE C# assemblies — project-side because compilation is
                                        per-project context (defines, engine version); pruned automatically
                                        when a package leaves the manifest
```

### A packaged (shipped) game

```text title="A packaged game"
<game>/
  Assets/ + .assetmanifest              project content + its GUID↔path manifest
  Packages/packages.index               the mount list (the staged layout IS the resolution — no re-resolve at boot)
  Packages/<alias>/Assets/ + .assetmanifest   per-package content, each an independent GUID namespace
  Packages/<alias>/NativeScripts/       native module DLL + relative record + engine-ABI marker
  Managed/Packages/<Asm>.dll            package C# (managed builds; AOT compiles sources into the single lib)
```

A Mac game is a `.app` bundle whose `Contents/Resources` is this `<game>/` folder. Its code lives in `Contents/Frameworks`, where the bundle's signature covers it: each package's native module is in `Contents/Frameworks/Packages/<alias>/`, and the record in `Packages/<alias>/NativeScripts/` points there. The export stages no package Editor module.

## Adding an asset to a package outside the editor

:::tip[Embedded and `file:` packages: yes, it just works]

Drop `coral.png` into `my-pack/Assets/Textures/` with Explorer while the editor runs (or before opening it): the package mount is **watched**, the watcher registers the file, the GUID derives deterministically from `hash(package-alias + relative-path)`. No editor round-trip is needed to "assign" it, because derived identity means the GUID is a pure function of where the file sits. The metadata record (type, KV) is written to **the package's own `AssetDatabase.assetdb`**, never the consuming project's, so when the package author commits their package folder, the metadata travels with it. There are no `.meta` sidecar files anywhere in this engine: identity needs no per-file sidecar, which is exactly why out-of-editor adds are safe. Same story for edits and deletes (watched → re-fingerprinted / tombstoned in the package DB).

:::

:::caution[Git packages: by design, you do not add files on the consumer side]

The cache entry is immutable and unwatched. A consumer adding files there would be editing a checkout that re-resolving replaces. The authoring flow is: the package author works on the package as a file:/embedded package (everything above applies, out-of-editor adds included), then publishes by pushing + tagging. Consumers bump the ref in their manifest → new cache entry → the new asset appears, with the *same GUID everywhere* because derived GUIDs are deterministic from alias+path. Optional at publish: freeze a `.assetmanifest` into the package to switch it to stored identity (GUIDs read verbatim: this is what makes GUIDs survive even a package *rename*, and it is how an existing project folder is extracted into a package with its original GUIDs intact).

:::

:::tip[Editing a package's C# code: recompiles live in embedded and `file:` packages]

While hot reload is on, saving a `.cs` (or `.csproj`) under the C# module root of an embedded or `file:` package starts the same reload a project script edit starts: every package module recompiles in dependency order, then the editor and project scripts, and the editor swaps them all at once. The Log panel prints `[Packages] compiled package assembly <Name>.dll (N ms)` for each module, where N is the compile server's round trip. If the module fails to compile, its errors stay in the Script Errors panel next to any project script errors until that module compiles again. The previous build keeps running in the meantime. Git and engine packages are not watched, because the cache never changes in place: to edit one, add a checkout of it by `file:` path, which takes precedence over the engine copy with the same name.

:::

:::tip[Shipping a prebuilt C# assembly: loads without a compile]

A package can ship a C# module as a compiled assembly instead of sources. Declare it in `package.json`: a `modules[]` entry with `"lang": "CSharp"`, the `kind` (`"Runtime"`, or `"Editor"` for the editor half), a `root`, and `"prebuilt": "Binaries/"`. Then put `<Assembly>.dll` (and its `.pdb` if you have one) in that directory. The assembly name is the one the package name derives (`closed-pack` → `ClosedPack`, or `ClosedPack.Editor` for the editor half). When the module has no `.cs` sources, the editor copies the declared DLL into `ScriptAssemblies/Packages/`, the same place a compiled module lands, and loads it with the other script assemblies. Nothing is compiled, so no compile server is needed for that module. The Log panel prints `[Packages] using prebuilt assembly <Assembly>.dll from <dir>`. Project scripts can use its types just as they use a compiled package's. A shipping (NativeAOT) build links the assembly in by reference.

**Sources win.** If the module has any `.cs` sources, it compiles from them and the declared DLL is not used (the Log panel says so). A module that gains sources switches to compiling when the project is reopened, and until then the Package Manager shows the change as pending. The declaration is the instruction: a DLL anywhere else in the package is a plain file and is never loaded. If the declared DLL is missing, the module is not loaded, and an error names the path the editor expected and the `modules[]` entry to fix.

:::

### What a game ships from a package

A game ships these package assets:

- the assets its scenes reference;
- the package's `Shaders/` folder;
- its code modules.

Code loads assets by path, and the export cannot see that. If the package's code loads assets that way, list them in `package.json`, keyed by the component whose code loads them. Each entry is a file or a folder, relative to the package's assets folder:

```json title="runtimeAssets in package.json"
"runtimeAssets": {
  "EZTree": ["Textures/EZTree/"]
}
```

A game ships the listed files, and what they reference, only when one of its scenes uses that component. A game without trees bakes none of the Tree Generator's textures. If a listed path matches no asset in the package, the export warns. If a game asks for an asset it does not have, the log shows `asset <id> is not in this build`, followed by the fix.

## GUID identity: the two modes, and when each applies

| Mode | How the GUID is determined | Used by | Survives |
|---|---|---|---|
| **Derived** (default) | `hash(alias + canonical-relative-path)`: deterministic, no stored state needed at all | project mount, embedded/file: packages, manifest-less git packages | fresh checkouts, machine moves, cache wipes: anything except renaming the package or moving the file |
| **Stored** | read verbatim from a shipped `.assetmanifest` (JSONL, committed/published with the package) | packaged games (always), git packages that publish a manifest, the extraction route above | everything, including package renames and file moves: the manifest IS the identity |

Cross-package references are plain GUID references and work in both modes because every mount is an **independent GUID namespace** (per-alias namespace hash: collisions between sources are impossible by construction).

## What compiles or derives where

| Data | Package | Project | Global cache | Why there |
|---|---|---|---|---|
| Asset files + identity metadata | ✔ (its `Assets/` and its `.assetdb`) | — | ✔ pristine copy (git) | identity travels with the package |
| Derived asset data (fingerprints, dep edges, import cache) | ✔ `.Cache` (mutable packages) | ✔ `.Cache` (project assets; git and engine packages under `.Cache/AssetDatabase/Packages/<alias>`) | — | always regenerable, never committed, safe to delete |
| Compiled C# assemblies | — | ✔ `ScriptAssemblies/Packages/` | — | compilation is per-project context (defines, engine build); auto-pruned on package removal |
| Native module builds | ✔ `.Cache/NativeScripts` (mutable) | — | ✔ `.native/<entry>` (git) | per-package caching without touching pristine payloads |
| Dependency pins | `package.json` declares ranges | ✔ manifest + lock (committed) | — | the project owns what it depends on |
| Prebuilt C# assemblies | ✔ the declared `prebuilt` dir | ✔ copied to `ScriptAssemblies/Packages/` | ✔ (inside the entry) | used only when the module has no sources; ship-without-compile |
| Prebuilt native binaries | ✔ `Binaries/<platform-fingerprint>/` | — | ✔ (inside the entry) | ship-without-toolchain; fingerprint-gated |
