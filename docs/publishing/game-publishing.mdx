The same Python commands prepare, verify, preview, and upload game releases on Windows, macOS, and Linux. Each project owns a `publishing.json`. Steam IDs are configuration, never engine constants. No Steam account is needed to prepare a release or to deploy it to a Steam Deck over SSH.

## Build host and target

| Operation | macOS host | Windows host | Linux host |
|---|---|---|---|
| Build a macOS game | macOS editor | Use a Mac | Use a Mac |
| Build a Windows game | Use a Windows machine | Windows editor | Use a Windows machine |
| Build a Linux game, including gameplay code | Use a Linux machine | Linux machine, or the Linux editor under WSL2 | Linux editor |
| Build the Steam Deck x64 runtime | Docker, `linux/amd64` (emulated on Apple Silicon) | WSL2 with Docker integration | Docker |
| Prepare, verify, SteamPipe upload | Yes | Yes | Yes |
| Deploy, roll back, startup smoke test on a Deck | OpenSSH | Windows OpenSSH | OpenSSH |

The editor refuses a target its host cannot build and says how to build it instead. The Windows editor, for example, refuses a Linux or Steam Deck build and names the Linux x64 editor and `build_deck.py` (in the engine checkout's `Tools/Scripts`). It does not write a Windows game into a folder named for the other target.

A runtime template is the engine executable and its libraries. A game containing C#, custom C++, or native package modules needs a machine that builds for the target, with the target's SDK. The editor refuses to leave that code out of a template export. Template exports and native builds stage assets, GUID manifests, packages, and game configuration the same way.

The editor stores the Steam Deck platform under the name `Steam`. In publishing configuration, `platform` is the binary's operating system, `deviceProfile` is an optional device preference, and `depotId` selects the Steam depot. One Linux depot can serve both Linux desktops and the Steam Deck. It does not need a separate Deck depot.

## First project setup

Install Python 3.10 or newer. Run these commands from the game project, replacing `/path/to/GameEngine` with your engine checkout (on Windows, use its Windows path). The scripts need only Python's standard library.

```bash title="Create publishing.json"
python /path/to/GameEngine/Tools/Scripts/publish_game.py init
```

Edit the generated `publishing.json`:

- Keep the targets you ship and set their output folders, executable paths, and `game.config` paths. Relative `source` paths resolve against the configuration file, not the shell's working directory. Executable and content paths use `/` on every host. Set the actual Mac `.app` name and architecture. A Mac export keeps code in `Contents/MacOS` and `Contents/Frameworks` (the engine, your native C++ scripts, and each package's native module) and everything else in `Contents/Resources`, so its executable is `My Game.app/Contents/MacOS/Player` and its `game.config` is `My Game.app/Contents/Resources/game.config`.
- Add your own `steam.appId` and each target's `depotId` before a Steam action. Null IDs are allowed for local release preparation and Deck deployment.
- Use `requiredFiles` for project-specific gameplay libraries or content whose absence must block publishing, including precompiled gameplay shipped without source.
- Keep `editorPlatform` to build with the open editor, or supply `buildCommands` for a build machine. Commands are arrays of arguments, grouped by host (`windows`, `macos`, `linux`). They must wait for the completed game export and return nonzero on failure. A configured host recipe takes precedence over the editor build.

For a Steam Deck export from the macOS editor, a target can use `platform: "linux"`, `architecture: "x64"`, `deviceProfile: "steamdeck"`, `editorPlatform: "Steam"`, `source: "Build/Steam/steamdeck-player"`, `executable: "Player"`, and `gameConfig: "game.config"`. Match `source` to your editor's actual output setting.

## What a build ships

A build ships the scenes in its scene list and the assets they reference, followed through materials, models, and every other reference, whether the asset belongs to the project or to a package. Each enabled package also ships:

- its `Shaders/` folder, because a material names its shaders by path;
- its code modules;
- the files its `package.json` lists under `runtimeAssets` for each component a shipped scene uses.

Nothing else from a package ships. A package that ships nothing is left out of the game, so editor-only packages such as the version control integrations add nothing to it. Only shipped textures are baked.

Every build has a `ThirdPartyNotices` folder beside `game.config`, with the licenses and notices of the third-party code in the engine. Keep this folder in every copy of the game that you distribute, because some of these licenses require it.

A script cannot be scanned for the assets it loads. If a script loads an asset by GUID or by path and nothing in a shipped scene references that asset, the asset is not in the build. When the game asks for it, the log shows `asset <id> is not in this build`, and the load returns nothing. To ship such an asset, reference it from a scene or a material in the build, or set its folder to `always` as the next paragraph shows. A package author instead lists the files the package's code loads by path under `runtimeAssets`, keyed by the component that loads them. See [the package data model](../packages/package-data-model.mdx#what-a-game-ships-from-a-package).

A folder can set what ships from it. Put a file named `.assetfolder` in the folder, with one key, `ship`, for example `{"ship": "always"}`. The key takes one of three values. With `always`, every asset in the folder and its subfolders ships, and so do the assets it references, even when no scene uses them. With `never`, no asset in the folder ships. If a shipped asset references one of them, or the scene list holds one, the export fails, and the error shows the chain of references, such as `Scenes/Castle.scene → Prefabs/Wall.prefab → Textures/Old/Wall.png`. With `inferred`, the default, an asset ships only when a shipped asset references it. The nearest `.assetfolder` above an asset sets its rule, so a subfolder with `inferred` inside an `always` folder ships only what is referenced. A file that is not valid JSON, has another key or value, or cannot be read fails the export with a sentence that names the file. The export reads these files only under the project's asset folder (`Assets/`). A `.assetfolder` inside a package is not read.

A web export puts `THIRD_PARTY_NOTICES.md` in the exported folder, beside `WebPlayer.html`. The file holds the licenses and notices of the third-party code in the web player and its shaders. Keep it in the folder when you publish the game, because some of these licenses require it. The file comes from the web player build, which writes it beside `WebPlayer.wasm`. If the player template has no notices file, the export stops and tells you to build the `WebPlayer` target again.

## Export requirements

Some exports need a tool on the build machine. A Mac export needs the Metal Toolchain. With it, the export compiles the shader stages that the game used in the editor into Metal libraries, and the game loads them instead of compiling those stages while it runs. Install the toolchain once:

```sh title="Install the Metal Toolchain"
xcodebuild -downloadComponent MetalToolchain
```

Without the toolchain, the export still succeeds. It shows a warning that names the install command, and the game compiles each shader stage when it first draws with it.

The editor records the shader stages that the open project uses in `.Cache/Pipelines/ShaderStages.txt` under the project folder, and the export reads that file. Play the scenes of the game in the editor before an export, so that the record holds their stages. A Player records in its user data folder, which the export does not read.

## Build, prepare, verify

Open the project and the Build panel (the **Build** button in the editor's top toolbar), and leave the panel open: `build` stops with an error while the panel is closed. [Your first project](../getting-started/first-project.mdx#export-your-game) covers creating a project and a plain export from the panel. The build command checks the connected project's identity, starts the chosen target, waits for that exact build's completion receipt, and validates its output. A different editor project, a failed script compile, a cancellation, a newer build, or a mismatched output folder stops the command.

```bash title="Build, check, prepare and verify a release"
python /path/to/GameEngine/Tools/Scripts/publish_game.py build --target windows
python /path/to/GameEngine/Tools/Scripts/publish_game.py check --target windows
python /path/to/GameEngine/Tools/Scripts/publish_game.py prepare --target windows --release 1.0.0-beta.1
python /path/to/GameEngine/Tools/Scripts/publish_game.py verify Releases/1.0.0-beta.1
```

Use `--editor-port` to select a particular editor. Editor builds also need Node.js and the engine's command-line tool dependencies. Custom build recipes do not. Select the native target on each machine. Copy completed outputs from other machines into the configured source folders, preserving `.app` symlinks and Unix permissions, then prepare several depots together by repeating `--target`. Omitting `--target` selects every configured target. `prepare` also works after an ordinary Build button export. It does not need the editor to stay open.

:::caution[How a build replaces its output folder]

A build writes into a staging folder next to the output folder and replaces the output only once everything has succeeded. If another program holds a file in the new build open, the build copies the files into place instead of moving the folder. The build keeps no copy of the previous output. To go back to an earlier version, use a prepared release (see `publish_game.py` below).

If the previous game is running, the build stops without changing anything: close the game, then build again. A `<output>.discard` folder holds files of a replaced game that were still in use. The next build deletes it.

`<output>.previous` exists only while a build replaces the output. If one is left behind, a build stopped at that step: the output folder may be incomplete and `<output>.previous` holds the game it was replacing. Move it back or delete it, then build again.

:::

Preparation copies the game into a new release directory and validates the startup scene and render pipeline, compiled shaders, asset identities, gameplay assembly paths, package mounts, and native module targets. It rejects external symlinks, paths that differ only by case, and development `steam_appid.txt` overrides. Loose PDB and `.debug` files move to `symbols/`, outside the depot content. Source outputs stay intact. Mac app bundles are copied without editing their signed contents. Configure any production signing and notarization in the Mac build recipe before preparation.

Every release has a checksum manifest. Reusing a release name is refused, and Steam and deploy actions recheck that the content has not changed. Use a new release name for changes. Carry native build outputs between machines in an archive that preserves symlinks and modes. Windows may need Developer Mode to extract Mac bundle symlinks. Test installed executable permissions in SteamPipe Preview when uploading Unix depots from Windows.

A Player whose `game.config` turns `window.vsync` off runs uncapped. To cap it, set the environment variable `GE_FRAME_CAP` to a frame rate before it starts (for example `GE_FRAME_CAP=60`).

To run a Player without sound, for example an automated test or a timing run on a shared machine, pass `--silent-audio` or set the environment variable `GE_AUDIO_OUTPUT=silent`. The flag wins when both are given. The game's audio is mixed as usual, so voices start, finish, and meter exactly as with sound, but no audio device is opened. The editor reads `GE_AUDIO_OUTPUT` the same way. Any value other than `silent` or `device` is ignored with a warning in the log.

The editor and the Player ask for the audio device. A program that starts the engine itself, through its own `ApplicationConfig`, opens no audio device by default: set `AudioOutput` to `Audio::AudioOutput::Device` to play sound on the system's default playback device. Tests and tools keep the default and mix on the Silent output.

## SteamPipe

Install the Steamworks SDK's SteamCMD/ContentBuilder for your platform. Log in interactively once with your build account and complete Steam Guard. Pass the executable or the `steamcmd.sh` wrapper with `--steamcmd`, or set `STEAMCMD`. Pass `--username`, or set `STEAM_BUILD_USER`. Passwords and tokens do not belong in the project configuration. SteamCMD owns the authenticated session.

```bash title="Preview and upload with SteamCMD"
python /path/to/GameEngine/Tools/Scripts/publish_game.py preview Releases/1.0.0-beta.1 --steamcmd /path/to/steamcmd --username YOUR_BUILD_ACCOUNT
python /path/to/GameEngine/Tools/Scripts/publish_game.py upload Releases/1.0.0-beta.1 --steamcmd /path/to/steamcmd --username YOUR_BUILD_ACCOUNT --branch YOUR_BETA_BRANCH
```

Preview generates file mappings and lets SteamCMD check them without uploading. Without `--steamcmd`, `preview` only writes reviewable VDF files. Upload is a separate command. Omit `--branch` to upload without setting the build live. The public/default branch is promoted in Steamworks, never by this tool. Scripts are regenerated against the current release location, so moving a release between machines does not leave stale absolute paths. SteamPipe's chunk cache lives beside the releases and is reused across versions.

Configure depot OS filters, launch options, and the Linux runtime in Steamworks. Depot uploads do not carry those app settings. Set the Linux launch option to `launch.sh` when shipping the Deck launcher, Windows to `Player.exe`, and Mac to the exported `.app`. See Valve's [uploading documentation](https://partner.steamgames.com/doc/sdk/uploading).

## Steam Deck iteration

Build the Deck runtime with the same entry point on every host:

```bash title="Build the Steam Deck runtime"
python /path/to/GameEngine/Tools/Scripts/build_deck.py --project . --output Build/DeckRuntime --check
python /path/to/GameEngine/Tools/Scripts/build_deck.py --project . --output Build/DeckRuntime
```

On Windows, install WSL2 and enable Docker Desktop integration for its default Linux distribution. The script converts paths and runs the Linux build inside WSL. Git Bash is not needed. On macOS and Linux it runs Docker directly. The runtime build keeps its dependency and compiler caches, lets only one build use the shared build tree at a time, and replaces the old output only with a completed build. `--check` never deletes the old game.

The container is `linux/amd64` on every host, emulated on Apple Silicon, and uses the pinned Steam Runtime 4 SDK for compilers, headers, and libraries. The .NET 10 SDK is staged separately. Select Steam Linux Runtime 4.0 in Steamworks for these releases, and qualify the exported game on that runtime and on the device before shipping. Valve recommends Steam Linux Runtime 4.0 for new native Linux games: [Steam Runtime documentation](https://github.com/ValveSoftware/steam-runtime).

### Steam Deck export from the macOS editor

The macOS editor packages a Steam Deck game into a cached Deck runtime. It uses the export tools staged with the editor, so no engine checkout is needed when a matching runtime is cached. Python 3 must be installed. A runtime matches when it was built from the same engine sources as the editor. After you rebuild the editor from changed engine sources, the next Deck export rebuilds the runtime in Docker, which needs the engine checkout. Runtimes without an identity, and runtimes whose binaries changed after they were built, are rebuilt the same way.

### Deploy to a Deck

Deploy a prepared Linux release. The Deck needs SSH key authentication and Python 3.12 or newer. Windows does not need rsync.

```bash title="Deploy, smoke-test and roll back on a Deck"
python /path/to/GameEngine/Tools/Scripts/publish_game.py deploy Releases/1.0.0-beta.1 --target linux --host deck@steamdeck.local --remote-dir devkit-game/MyGame
python /path/to/GameEngine/Tools/Scripts/publish_game.py smoke --host deck@steamdeck.local --remote-dir devkit-game/MyGame
python /path/to/GameEngine/Tools/Scripts/publish_game.py rollback --host deck@steamdeck.local --remote-dir devkit-game/MyGame
```

The remote directory is relative to the SSH user's home. Each deployment unpacks into a new release, verifies the transferred checksums, then switches `current` to it. The old release remains as `previous`. Rollback switches back without copying. Point the Steam development shortcut at `/home/deck/devkit-game/MyGame/current/launch.sh` once. A plain Linux export without the launcher can use `--launcher Player` for smoke testing if the desktop session environment is already configured. Add `--key` for a non-default SSH key.

The smoke command checks shared-library resolution, launches its own Player for up to 30 seconds, requires the initialization and startup-scene log markers, and stops only that process group. Logs remain under `~/.local/state/GameEngine/publishing` on the Deck. It is a startup check, not Deck Verified status or a performance benchmark. Before promoting a release, test controller-only navigation, keyboard entry, suspend and resume, offline startup, 1280×800 text readability, and sustained frame pacing on the device. The shared launcher keeps the descriptor-buffer and WSI fallbacks. Set `GE_VK_USE_DESCRIPTOR_BUFFER=1` or `GE_DECK_WSI_BYPASS=0` when comparing driver behavior during qualification.

## Validation

From a build directory configured with tests enabled:

```bash title="Run the publishing contracts"
ctest -R "GamePublishingTests|BuildOutputPromotionTests" --output-on-failure
```

or run the Python contracts directly with `python Tests/GamePublishingTests.py`. `GamePublishingTests` is registered only when CMake finds Python 3.10 or newer.

:::caution[Some contracts run only on Linux or macOS]

The Steam Deck build preflight and the Deck receiver's install and rollback run only on Linux or macOS, and the symlink rejection needs symlink support (Developer Mode on Windows). On Windows those tests report as skipped.

:::
