---
title: Gradient-aware deband
description: The deband filter in the terminal encode that breaks up visible banding in 8-bit gradients, how a Post Process Volume turns it on, where it runs, and what it does to a pixel.
---

Content authored as an 8-bit gradient can reach the screen as a visible staircase once lighting and exposure gain magnify each authored step into several output code values. The dither cannot break a step several times its own amplitude, so the engine carries a gradient-aware deband filter in the terminal encode. It is **off unless a volume turns it on**.

## Turning it on

Attach a `DebandEffect` component to the same entity as a `PostProcessVolume`. A world with no volume, and a volume with no `DebandEffect`, run with the filter off. Attaching the component is the explicit enable, and `Enabled = false` is an explicit pin-off. `ThresholdLsb` lerps across volume blends like any other volume property.

| Control | Default | Meaning |
|---|---|---|
| `DebandEffect.Enabled` | true (component absent = filter off) | Whether this volume engages the filter. |
| `DebandEffect.ThresholdLsb` | 6 | The gate, in output code values of the target's own bit depth. A tap average is adopted only while *every* channel stays within this distance of the original pixel, so a real edge vetoes the blend. Clamped 0–16; 0 is off. Larger gates start eating texture detail. |
| `GE_DEBAND` | on | Debug instrument: `0` kills the filter process-wide and beats any volume. Also the A/B and capture-parity gate. |
| `GE_DEBAND_THRESHOLD` | unset | Debug override for the gate; beats any volume value (clamped 0–16, 0 disables). |
| `GE_DEBAND_RADIUS` | 8.0 | Debug override for the first-iteration tap radius in pixels (clamped 1–64, ×i per iteration). Process-wide, not a volume knob. |

Precedence is resolved in one place, `Passes::ResolveOutputDebandThresholdLsb()`: environment kill → environment threshold override → the volume value. The environment is read once per process. The volume value flows per frame from `PostProcessSettings::DebandThresholdLsb` to every terminal-encode call site, movie encodes included. Radii and iteration count are compile-time.

## Where it runs

Inside the terminal encode (`encode_srgb.frag` / `AddSRGBEncodePassRG`), between the output transfer curve and the TPDF dither:

```text title="The terminal encode, with the deband step"
FinalLinear (FP16) ─→ EncodeForOutput (sRGB / PQ / HLG) ─→ DebandEncoded ─→ TPDF dither ─→ quantizing target
```

The bands are output-referred (they are born from albedo × lighting × exposure and are measured in output code values), so the filter belongs after the transfer curve, where one threshold means the same thing whatever the exposure is. It is one pass with no new render-graph resources, and it costs nothing when off: `debandThreshold ≤ 0` is a dynamically uniform branch, so the taps never issue. scRGB and hardware-sRGB passthrough carry no quantizer in this pass and get neither dither nor deband.

## What it does to a pixel

Three iterations; each takes a 4-tap cross at a per-pixel random rotation and distance, with the radius growing per iteration (8/16/24 px reach by default) so it covers plateaus of the widths a camera actually produces. Each tap samples the source and applies the active transfer curve, and the four-tap average is compared against the *original* encoded center, never the evolving result, which is what bounds total displacement to one threshold. The average is adopted only when every channel passes the gate, which keeps hue stable and lets one high-contrast channel veto the blend. The dither then breaks the residual sub-code-value structure. Its amplitude is unchanged.

The threshold is always scaled by the destination's own quantizer step (`EncodeDitherLsbForFormat`: 1/255 for 8-bit, 1/1023 for RGB10A2, nothing for a float target), the same sizing rule the dither amplitude uses. Neither filter can be sized for a depth the target does not have.

## Editor views and editor chrome

Editor chrome is never debanded, and this is structural rather than a list of rectangles to avoid. Each editor world view finalizes at its own resolve (`Engine::Renderer::DeclareViewFinalize` applies the transfer curve, this deband, and the dither to that view's image alone), and the interface composites onto the finished result. The window's terminal encode then names `FinalizeQuantizer::None` and filters nothing: it rounds the composite onto the backbuffer's step and adds neither filter. Editor viewport pixels therefore run exactly the filter the player runs, so the volume lever previews truthfully.

Views finalize only while `Engine::Renderer::ViewFinalizeEligible` holds, which means no active HDR output mode. Under HDR the views decline, the terminal encode owns the transfer curve and its quantizer full-frame, and the chrome exclusion does not apply: the 10-bit step puts that grain at about 0.1%.

## Limits

- Anything composed into a view's image *before* its finalize is filtered with the world: scene-pane overlay and gizmo passes write into the pipeline output the finalize consumes, so in-viewport overlays are debanded too, bounded to under one threshold and mostly vetoed by contrast. The game view's HUD composites onto the finished view and is never filtered.
- World-content previews that do not finalize (asset previews, camera-bookmark previews, thumbnails, the video player) are not debanded at all.
- A profiled strip laid across a diagonal high-contrast edge manufactures a synthetic staircase and looks exactly like banding in the numbers. The filter correctly refuses to smooth those. Check a strip is edge-free before reading its steps as banding.

## Checking it is alive

The backbuffer state log line carries `debandThreshold` and `debandRadius`, and `get_render_stats` reports the effective gate as `debandThresholdLsb` in its `output` block, so a filter that is off reads as off rather than having to be seen.
