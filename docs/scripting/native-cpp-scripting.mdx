Author components and systems against the engine's C++ API.

## Overview

Native project scripts compile into a separate user module against the staged SDK beside the editor. The SDK supplies the module entry points. Component and system registration can be generated from headers. Keep the SDK, engine, and user modules from the same build and configuration.

## Project layout

Put project headers and C++ sources under the project's `Assets` directory. The project module is named `UserScripts`. The editor generates its CMake project in `Assets/CMakeLists.txt`, builds under `.Cache/NativeScripts/build`, and loads versioned copies from `.Cache/NativeScripts/active`. Generated CMake content is owned by the generator and is overwritten when its inputs change.

```text title="A project's native script layout"
MyGame/
  Assets/
    Scripts/
      EnemyHealth.h
      DamageSystem.h
      DamageSystem.cpp
    CMakeLists.txt                 # generated
  .Cache/NativeScripts/
    build/                        # generated build and cache record
    active/                       # loaded module copies
```

Packages declare their own native modules. Each package module has a separate generated project, build directory, and active directory in its writable derived cache. An Editor-kind module also links the EditorSDK. See the [package data model](../packages/package-data-model.mdx) for module declarations and source ownership.

## Your first component

For automatic registration, define the component in a `.h` or `.hpp` file and inherit the component tag:

```cpp title="Assets/Scripts/EnemyHealth.h"
#pragma once
#include <GameSDK/Component.h>

struct EnemyHealth : ECS::ComponentBase
{
    float Current = 100.0f;
    float Maximum = 100.0f;
};
```

The build scanner finds tagged components in headers and generates their registration. A tagged component defined only in a `.cpp` file is not scanned.

The scanner does not run the preprocessor. It skips the lines of an `#if 0` branch and reads every branch of any other condition. A component that a macro declares is not registered. The scan warns with the macro's name, so declare the struct directly or register it with `GE_REGISTER_COMPONENT`. A component's name must be ASCII. A component with any other name is listed as skipped.

### Marker comments

A component the component scanner registers takes marker comments that change how the editor and the build treat it: the engine's own components, and a component a game declares in a header as `struct EnemyHealth : ECS::ComponentBase` (`GameSDK/Component.h`). A marker is a `//` line comment. A struct marker sits on the line of the `struct` or in the comment lines directly above it. A field marker sits on the field's line or directly above it. Text after the marker is free.

```cpp title="Component and field markers"
#include <GameSDK/Component.h>

// Where the designer marked a spawn: drawn by an editor gizmo, never shipped.
// @ge-no-add        added by the spawn tool, not from the Add Component menu
// @ge-editor-only
struct SpawnHint : ECS::ComponentBase {
    float Radius = 2.0f;      // @ge-range 0.5 50
    int   PlacedBy = 0;       // @ge-readonly
    float Weight = 1.0f;      // @ge-tooltip "Relative chance against the other hints"
};
```

| Marker | On | Effect |
|---|---|---|
| `@ge-no-add` | struct | The component registers, loads and saves as usual but stays out of the Add Component menu. Use it for a component a tool or a system adds, where a hand-added one would be wrong. |
| `@ge-editor-only` | struct | The component loads, saves and shows in the editor as usual. A game export removes its lines from every scene and prefab it ships, so the shipped scene has no trace of it. The entity stays, with its other components and its children. Use it for annotations only the editor reads. |
| `[DoNotSerialize]` | struct or field | Never saved or loaded: runtime state rebuilt every session. On a field, only that field. |
| `@ge-readonly Writer` | struct | The engine owns the component, and `Writer` (the text after the marker) is the system that writes it. Its C# mirror is read-only, and a script's `ComponentType<T>.Set` is refused with an error that names the writer. |
| `@ge-engine-internal Writer` | struct | Engine runtime state, no game API: the component has no C# mirror and no web type, and a script cannot write it. `Writer` is the system that writes it. |
| `@ge-tag` | struct | A struct with no fields is a component (a tag that an entity has or not). A struct with no fields and no marker is not a component. |
| `@ge-readonly` | field | Shown in the inspector, not editable there. In the C# mirror the field is get-only, and a script's write keeps the engine's value. |
| `@ge-hidden` | field | Not shown in the inspector and not saved in scenes. The C# mirror has no member for it, and a script's write keeps the engine's value. |
| `@ge-tooltip Text` | field | The inspector's tooltip for the field; the text may be quoted. |
| `@ge-label Text` | field or enumerator | The words the inspector shows for the field's row or for the enumerator in a dropdown, in place of the name split into words (`RaysPerProbe` reads "Rays Per Probe"); the text may be quoted. On an enumerator, put it on the enumerator's line or on the line above. The scene file and the C# mirror keep the C++ name. A label on a `@ge-hidden` field is ignored, with a build warning. |
| `@ge-range Min [Max]` | float field | The inspector clamps edits to the range; without `Max` the range is open above. |

A field that refers to an asset is an `AssetRef<AssetType::...>` (`Components/AssetRef.h`), for example `AssetRef<AssetType::Audio> Sound;`. The inspector shows an asset picker for that asset type, and a scene saves the asset's GUID. The scanner skips a component that has a pointer, a reference, a `std::` container or any other template type in a field, and the build output names the component and the field.

### Explicit registration

When explicit registration is needed, include `GameSDK/GameSDK.h` and list the fields in `GE_REGISTER_COMPONENT`. This also works in a C++ source file:

```cpp title="Explicit registration"
#include <GameSDK/GameSDK.h>

struct EnemyHealth
{
    float Current = 100.0f;
    float Maximum = 100.0f;
};
GE_REGISTER_COMPONENT(EnemyHealth, Current, Maximum);
```

These are alternative declarations of the same example. Use one registration path for a type.

## Adding a system

Define a native system in a header with `GameSDK/System.h`. The scanner generates its registration from the `ECS::SystemBase` base:

```cpp title="Assets/Scripts/DamageSystem.h"
#pragma once
#include <GameSDK/System.h>
#include "EnemyHealth.h"

struct DamageSystem : ECS::SystemBase
{
    void OnUpdate(ECS::World& world, float dt)
    {
        world.Query<ECS::Write<EnemyHealth>>().Each(
            [dt](ECS::EntityHandle, EnemyHealth& health)
            {
                health.Current -= dt;
                if (health.Current < 0.0f)
                    health.Current = 0.0f;
            });
    }
};
```

`OnStart`, `OnUpdate`, `OnPostSimulation`, and `OnDestroy` are optional hooks. Their ordering and permitted world access are defined in [Native User Systems](./native-user-systems.mdx). Use that contract when choosing between gameplay before simulation and presentation after simulation.

User systems run in ascending order of a `static constexpr int Order` member, 0 when a system declares none; give a system an `Order` when it must run after another in the same frame. See [the order systems run in](./native-user-systems.mdx#the-order-systems-run-in).

## Input

A system reads the game's input from `EngineCore::GetInstance().GetRuntimeInput()` (`Core/Engine.h`), an `Input::InputSystem`: keys, mouse buttons, the mouse position and delta, and pointer lock for mouse look.

The API, its contract and how the editor and the Player deliver input are in [The input system](../input/input-system.mdx).

## Reloading

The native script manager watches source changes and rebuilds the affected module. Build output and errors are reported through the editor's log. It validates the candidate module's ABI and toolchain fingerprint before accepting it. A failed build is not a successful reload: read the diagnostic before continuing.

Build duration depends on the source and toolchain. Component data restoration and module replacement have failure paths. Keep authored scenes saved rather than relying on a reload to preserve every live change.

### Play mode

User systems start when Play begins and stop when Play ends. `OnUpdate` runs before the engine simulation. `OnPostSimulation` runs later in the scheduled frame. See [the lifecycle guide](./native-user-systems.mdx) for delivery, pause, and reset behavior.

## Editor extensions

Custom inspectors and gizmos use the editor's registries from an Editor-kind package module. A folder named `Editor` inside project scripts does not by itself declare a separate EditorSDK module. See [package module kinds](../packages/package-data-model.mdx) and the [editor development guidelines](../contributing/editor-dev-guidelines.mdx) before adding editor-only dependencies.

For game UI, use the engine's UI API and authored UXML/CSS. See [game UI scaling](../ui/game-ui-scaling.mdx) for the canvas and layout contract.

## Shipping a Player build

Export from the editor's [game publishing workflow](../publishing/game-publishing.mdx). The export stages compatible prebuilt runtime modules and their load records. The shipped Player loads those modules without a compiler. Editor-kind modules do not ship.

The native gameplay module and the Player application have distinct source ownership. See [Desktop Player source ownership](../publishing/desktop-player-source-ownership.mdx) before adding a custom application entry point.

## IDE integration

The generated CMake project carries the SDK include directories, import libraries, and compile definitions. Engine-driven configuration passes the current `GAMEENGINE_SDK_DIR`. The generated file's baked path is a last-known-good IDE default. Let the editor regenerate the project after changing engine installations.

## When things go wrong

- **No native scripting:** check that the staged SDK manifest is present beside the editor and that the build log reports a usable toolchain.
- **A component does not register:** put its tagged declaration in a header, or use explicit registration with the field list.
- **A module is refused:** rebuild it against the matching engine and configuration. An ABI or fingerprint mismatch is not bypassed.
- **A build fails:** inspect the compiler output under `.Cache/NativeScripts/build` and the editor log.
